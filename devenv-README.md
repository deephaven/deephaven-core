# devenv.sh dev environment for deephaven-core

A reproducible dev toolchain (bootstrap JDK, Node, Python, C++) for this
repo, built on [devenv.sh](https://devenv.sh).

## What's here

- **`devenv.yaml`** — inputs only. Uses devenv's own default nixpkgs input
  (`github:cachix/devenv-nixpkgs/rolling`) rather than an arbitrary
  `nixos-unstable` pin — the branch devenv itself is tested against.
- **`devenv.nix`** — the actual environment. Read its header comment first;
  it explains scope/rationale inline. In short:
  - `languages.java` — Temurin 21 (`pkgs.temurin-bin-21`), matches
    `.devcontainer/project.Dockerfile`'s JDK and what Gradle 9.7.1 (this
    repo's wrapper version) needs to launch. `JAVA_HOME` is set
    automatically by the module.
  - `languages.javascript` — `pkgs.nodejs_24`, tracks
    `web/client-api/types/.nvmrc` (`v24.10.0`) at the major-version level;
    devenv has no `.nvmrc` auto-detection, so this is a manual pin.
  - `languages.python` — `pkgs.python312`, matches
    `.github/workflows/quick-ci.yml`'s `python-version: '3.12'`.
  - `languages.cplusplus` (LSP/debugger only) + explicit `packages` for the
    real toolchain (`cmake`, `gcc`, `zlib`, `bzip2`, `openssl`,
    `pkg-config`), mirroring `cpp-client/README.md`'s `apt install` line.
    `gcc`/`gnumake` are also there for `py-server`'s `jpy` JNI bridge,
    which compiles a native extension against the Python above.
  - Gradle wrapper vendoring + toolchain isolation, via
    **`nix/gradle-wrapper.nix`** (a plain `{ pkgs, wrapperPropertiesFile }`
    function, no devenv-specific coupling). Reads `gradle-wrapper.properties`
    as the single source of truth, fetches+unpacks that exact Gradle
    distribution into the Nix store, and pre-seeds
    `$GRADLE_USER_HOME/wrapper/dists/...` so `./gradlew` never needs
    network access for its own download. Also redirects `GRADLE_USER_HOME`
    to an isolated, symlink-backed directory (nothing duplicated/
    re-downloaded) whose own `gradle.properties` sets
    `org.gradle.java.installations.auto-detect=false` and
    `...auto-download=false`, so Gradle only ever sees the JDK this file
    provides. **This means anything that wants a different JDK (e.g. this
    repo's nightly CI matrix, `-PtestRuntimeVersion=17/25`) will fail with
    "no matching toolchain found" in this shell** — pass
    `-Porg.gradle.java.installations.auto-download=true` to override
    locally if you need to reproduce that.
  - `DOCKER_HOST` auto-detection: on shell entry, if `DOCKER_HOST` isn't
    already set and `podman` is on `PATH`, queries
    `podman info --format '{{.Host.RemoteSocket.Path}}'` (Podman's own
    reported socket location — confirmed against `podman-info(1)`, not
    guessed) and exports `DOCKER_HOST`/`TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE`
    if that path is an actual live socket. This is what lets
    Testcontainers/the gradle-docker-plugin find a rootless Podman socket
    without hardcoding a UID-specific path like
    `/run/user/1001/podman/podman.sock` (that path varies per machine/user
    — it's `$XDG_RUNTIME_DIR/podman/podman.sock`, i.e. embeds whoever's
    running the shell). Never overrides an already-set `DOCKER_HOST`, and
    never starts or configures the socket/service itself — see "What's NOT
    here" below.
- **`.envrc`** — `eval "$(devenv direnvrc)"` + `use devenv`, for direnv
  users; run `direnv allow` once.
- **`devenv.lock`** — generated by devenv itself (`devenv shell`/
  `devenv update`), analogous to `flake.lock`. Commit it; don't hand-edit.

## What's NOT here (deliberately)

- **No Docker/Podman provisioning.** `testOutOfBand` Testcontainers tests
  (`extensions/kafka`, `extensions/iceberg/s3`, etc.) and the bmuschko
  gradle-docker-plugin's `:docker-*` subprojects need a real Docker-API
  endpoint — this file assumes your host already has Docker or Podman
  installed and running normally (e.g. `systemctl --user enable --now
  podman.socket`), same as it would for any other project; it only
  *detects* and wires up what's already there (see `DOCKER_HOST`
  auto-detection above), it doesn't install or start anything. devenv's
  own `containers.*` option builds OCI images from this environment; it is
  *not* a Docker-API-compatible daemon/socket, so it wouldn't help here
  anyway.
- **No `devc.sh`/sandbox integration.** This is a plain host-side
  environment only.
- **No `git-hooks.nix`.** Mechanically it could run
  `./gradlew spotlessApply` on commit, but Gradle's startup/configuration
  overhead across 200+ subprojects makes it a poor fit for a *blocking*
  pre-commit hook. Also note: as of devenv 2.0, the `git-hooks` input is no
  longer bundled by default and would need adding to `devenv.yaml`
  explicitly if this is revisited.
- **No `services.*`** (devenv has native `services.kafka`/`services.minio`
  modules that could back local integration testing more conveniently) and
  **no `tasks.*`** definitions — the Gradle task graph already covers
  everything needed; nothing concrete has motivated adding either yet.

## Using it

Requires Nix (devenv is not self-bootstrapping): install it first, the
usual way for your platform. Then either:

```bash
# One-off, no persistent install:
nix run nixpkgs#devenv -- shell

# Or install devenv once, then just:
nix profile install nixpkgs#devenv
devenv shell

# direnv users, after the above:
direnv allow   # picks up .envrc automatically from then on
```

First entry downloads the whole toolchain (JDK, Node, Python, gcc, cmake,
etc.) plus devenv itself if not already installed — expect it to take a
while. Subsequent entries are near-instant (confirmed: ~0.2s) since
everything is cached in the Nix store.

## Verified (2026-09, this branch's initial commit)

Ran directly via `nix run nixpkgs#devenv -- shell -- <cmd>` in a throwaway
environment, not just inspected:

| Check | Result |
|---|---|
| `java -version` / `$JAVA_HOME` | Temurin 21.0.11, `JAVA_HOME` correct |
| `node --version` | v24.19.0 |
| `python3 --version` / `gcc --version` | 3.12.14 / gcc 15.3.0 |
| `cmake --version` / `pkg-config --version` | 4.3.4 / 0.29.2 |
| `./gradlew --version --offline` | Gradle 9.7.1, zero network access needed |
| `./gradlew javaToolchains --offline` | exactly one JDK listed (Temurin 21, Nix store path), auto-detect/auto-download both `Disabled` |
| `./gradlew :engine-table:compileJava` | `BUILD SUCCESSFUL`, 93 tasks |
| Second `devenv shell` entry | ~0.2s (properly cached) |

The `DOCKER_HOST` auto-detection hook was verified separately against all
four cases it needs to handle correctly (no `podman` on `PATH`; `podman`
present but the reported socket path isn't live; `podman` present with a
live socket — `DOCKER_HOST` gets set; `DOCKER_HOST` already set — left
untouched), by extracting the hook body and running it directly against a
stand-in `podman` binary for each case. Also observed correctly *not*
clobbering a real, already-set `DOCKER_HOST` pointing at a live Podman
socket in a container where it was set externally.

If any of these regress, that's the first thing to check before assuming
the `languages.*`/`nix/gradle-wrapper.nix` config itself is wrong — could
just as easily be a devenv/nixpkgs upstream change (re-run
`devenv update` and compare `devenv.lock`) or a real drift between the
sources of truth listed above (`gradle-wrapper.properties`, `.nvmrc`,
`quick-ci.yml`, `cpp-client/README.md`) and what's pinned in `devenv.nix`.

## Keeping versions in sync

Nothing here is auto-synced with its source of truth — if one of these
changes, update `devenv.nix` to match:

| Pinned here | Source of truth |
|---|---|
| `bootstrapJdk` (Temurin 21) | `.devcontainer/project.Dockerfile`'s JDK install |
| Gradle distribution (via `nix/gradle-wrapper.nix`) | `gradle/wrapper/gradle-wrapper.properties` (read automatically, not hand-copied) |
| `languages.javascript.package` (Node 24) | `web/client-api/types/.nvmrc` |
| `languages.python.package` (3.12) | `.github/workflows/quick-ci.yml`'s `python-version` |
| C++ toolchain packages | `cpp-client/README.md`'s `apt install` line |
