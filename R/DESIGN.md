# Deephaven R Client (`rdeephaven`) — Design & Implementation

Orientation document for engineers and coding agents who need to change code in `R/`. It describes
*how the client works* and *where things live*, so you can go straight to the right file instead of
discovering the layout by grepping.

Companion docs:

- `R/rdeephaven/BUILDING.md` — the user-facing build guide: install prerequisites, step-by-step build,
  common errors, running under Valgrind/gdb, code styling. **Read that one for "how do I build it";
  read this one for "how does it work".**
- `cpp-client/DESIGN.md` — design/implementation of the C++ client that this package wraps.
  Almost every question of the form "what does this operation actually do on the wire" is answered there.
- `cpp-client/BUILDING.md` — how to build and install the C++ client + its dependencies (a hard
  prerequisite for building this package).
- `R/rdeephaven/vignettes/*.Rmd` — user-facing tutorials (`rdeephaven`, `agg_by`, `update_by`).
- Generated API reference is published at <https://deephaven.io/core/client-api/r/>.
- Repo root `AGENTS.md` — the Java engine/server side of the system.

**How to use this file:** the section headings below are stable anchors. `grep -n '^## ' R/DESIGN.md`
to get the map, then read only the sections you need.

## 2. Build, install, test

**The C++ client is a hard prerequisite.** `src/Makevars` links `-ldhclient -ldhcore` out of
`$DHCPP/lib` and takes headers from `$DHCPP/include`, so you must first build and install the C++
client per `cpp-client/BUILDING.md`, then `source $DHCPP/env.sh` (which sets `DHCPP`, `CMAKE_PREFIX_PATH`,
`LD_LIBRARY_PATH`, `NCPUS`).

```bash
source /path/to/dhcpp/env.sh
cd R/rdeephaven && ../r-build.sh            # or, manually:
cd R && R CMD build rdeephaven && R CMD INSTALL --no-multiarch --with-keep.source rdeephaven_*.tar.gz
```

`r-build.sh` refuses to run unless `DHCPP`, `NCPUS`, and `LD_LIBRARY_PATH` are set and the working
directory looks like an R package root; it deletes `src/*.o` and `src/*.so` before and after, so every
build starts clean. Use `R CMD build`/`INSTALL` rather than `install.packages()` so the vignettes get
built.

`LD_LIBRARY_PATH` must also be set **at run time** — `library(rdeephaven)` fails with
`libdhclient.so: cannot open shared object file` otherwise. See `rdeephaven/BUILDING.md` for the
`.Renviron` / `rserver.conf` recipes (`etc/generate-*.sh` print the right lines).

Notable `Makevars` details:

- `CXX_STD = CXX17` — must match the C++ client.
- The protobuf library name is auto-detected: `-lprotobufd` if `$DHCPP/lib/libprotobufd.so` exists,
  else `-lprotobuf`. (The C++ dependency build names it `libprotobufd` for `Debug` builds.)
- gRPC link flags come from `pkg-config --libs grpc++` with `PKG_CONFIG_PATH=$DHCPP/lib/pkgconfig`.
- Include paths are hard-coded to `/usr/share/R/include` and
  `/usr/local/lib/R/site-library/Rcpp/include` — a non-standard R or Rcpp install needs an edit here.
- There is a commented-out address-sanitizer block; enabling it also requires an ASan-enabled R build.

**Tests** are integration tests and need a running Deephaven server. `inst/tests/testthat/helper.R`
reads `DH_HOST` (default `localhost`) and `DH_PORT` (default `10000`).

```r
library(testthat); test_package("rdeephaven")
```

**Gradle/CI** (`R/build.gradle`) layers Docker images: `:cpp-client:cppClient` → `rClient`
(runs `r-build.sh`) → `testRClient` (runs `r-tests.sh` against a containerized server, emits JUnit
XML), plus `rClientDoc` (roxygen; copies results back into `rdeephaven/man/`) and `rClientSite`
(pkgdown; copies into `rdeephaven/docs/`). `tasks.check.dependsOn(testRClient)`.
Note `build.gradle`'s `copyIn` lists files explicitly — a new top-level file in the package will not
reach the Docker build unless you add it there.

## 3. Layered architecture

```
 user R code
   │   Client$new(...) · th$update("X = i") · th$agg_by(agg_sum("Y"), by="X") · as.data.frame(th)
   ▼
 R6 layer          R/*.R
   │   validates arguments (verify_*), unwraps R6 objects (strip_r6_wrapping),
   │   forwards to $.internal_rcpp_object, re-wraps results in R6
   ▼
 Rcpp module       src/client.cpp — RCPP_MODULE(DeephavenInternalModule)
   │   INTERNAL_Client · INTERNAL_TableHandle · INTERNAL_ClientOptions ·
   │   INTERNAL_AggOp · INTERNAL_UpdateByOp · INTERNAL_OperationControl
   ▼
 C++ wrapper classes   ClientWrapper · TableHandleWrapper · ClientOptionsWrapper ·
   │                   AggregateWrapper · UpdateByOpWrapper   (each holds one C++ client object)
   ▼
 Deephaven C++ client  deephaven::client::{Client, TableHandleManager, TableHandle, Aggregate,
   │                   UpdateByOperation, ClientOptions}   → gRPC + Arrow Flight → server
   ▲
   └── bulk data crosses back and forth as an ArrowArrayStream C struct (§6), never as R vectors
```

Key design decisions:

- **The R client is a veneer, not an implementation.** Every Deephaven capability must exist in the
  C++ client first; the R layer only marshals arguments and results. If a feature is missing here,
  the first question is whether `cpp-client` has it (see `cpp-client/DESIGN.md` §4).
- **Three names per operation.** R method (`snake_case`) → Rcpp module method name (`snake_case`
  string) → C++ wrapper method (`CamelCase`) → C++ client method. E.g.
  `th$update_view(...)` → `.method("update_view", &TableHandleWrapper::UpdateView)` →
  `TableHandle::UpdateView`. Adding an operation means touching all of them. Watch for deliberate
  renames: R `group_by` → `TableHandleWrapper::GroupBy` → C++ `TableHandle::By`;
  R `join` → `TableHandleWrapper::CrossJoin` → C++ `TableHandle::CrossJoin`;
  R `open_table` → `ClientWrapper::OpenTable` → C++ `TableHandleManager::FetchTable`.
- **Every wrapper owns exactly one C++ object**, in a private member named `internal_*`
  (`internal_tbl_hdl`, `internal_agg_op`, `internal_update_by_op`, `internal_options`,
  `internal_client`). Every R6 class stores the Rcpp object in a public field named
  `.internal_rcpp_object`.
- **Lifetime is R's job.** `ClientWrapper` holds the `Client` in an `Rcpp::XPtr`, so R's GC decides
  when the connection is destroyed; the comment in `client.cpp` notes this is deliberate because the
  enterprise client may hold additional references. Every method that returns a new table returns a
  raw `new TableHandleWrapper(...)`; Rcpp modules take ownership of that pointer.
- **Errors propagate as C++ exceptions**, which Rcpp converts into R conditions. The R layer adds its
  own `stop()` calls for argument validation before ever reaching C++.

## 4. The R API surface

Two R6 classes carry the whole user-facing API.

### `Client` (`R/client_wrapper.R`)

`Client$new(...)` dispatches on the first argument: an `externalptr` goes to `initialize_for_xptr()`
(adopting a connection created elsewhere — this is the hook the Deephaven enterprise client uses);
anything else goes to `initialize_for_target(target, auth_type, ...)`.

`initialize_for_target` is where all connection policy lives — it is pure R, and it translates
friendly arguments into `INTERNAL_ClientOptions` calls:

| `auth_type` | what it does |
|-------------|--------------|
| `"anonymous"` (default) | `set_default_authentication()` |
| `"basic"` | requires *either* `username` + `password` *or* `auth_token`; joins them as `user:password` and calls `set_basic_authentication()`, which base64-encodes and sends `Basic <token>` |
| `"psk"` | `set_custom_authentication("io.deephaven.authentication.psk.PskAuthenticationHandler", auth_token)` |
| anything else | treated as a custom authenticator name: `set_custom_authentication(auth_type, auth_token)` |

It also validates `session_type` (`"python"` or `"groovy"` only), handles `use_tls` /
`tls_root_certs`, forwards `int_options` / `string_options` / `extra_headers`, and emits `warning()`s
for arguments that were set but will be ignored.

Methods: `empty_table(size)`, `time_table(period, start_time = "now")`, `open_table(name)`,
`import_table(table_object)`, `ticket_to_table(ticket)`, `run_script(script)`, `close()`.

`open_table` first calls the private `check_for_table()` so a missing table produces a clean R error
instead of a C++ exception; on the C++ side `CheckForTable` is implemented by attempting a
`FetchTable` inside a `try`/`catch` — i.e. it costs a round trip.

`import_table` dispatches on `class(table_object)[[1]]`: `data.frame` and `tbl_df` are converted with
`arrow::arrow_table()`, `Table` with `as_record_batch_reader()`, and `RecordBatchReader` goes
straight to the private `rbr_to_dh_table()` (§6).

### `TableHandle` (`R/table_handle_wrapper.R`)

Constructed only internally — its `initialize` rejects anything that is not an
`Rcpp_INTERNAL_TableHandle`. Grouped into four blocks in the file:

1. **Metadata**: `is_static()`, `bind_to_variable(name)`.
2. **Base-R-shaped**: `head(n)`, `tail(n)`, `nrow()`, `ncol()`, `dim()`, `merge(...)` — each also
   exposed as an S3 method at the bottom of the file.
3. **Conversion**: `as_record_batch_reader()`, `as_arrow_table()`, `as_tibble()`, `as_data_frame()` —
   all funnel through `as_record_batch_reader()` (§6), also exposed as S3 methods.
4. **Deephaven table operations**: `select`, `view`, `update`, `update_view`, `drop_columns`,
   `where`, `group_by`, `ungroup`, `update_by`, `agg_by`, `agg_all_by`, `first_by`, `last_by`,
   `head_by`, `tail_by`, `min_by`, `max_by`, `sum_by`, `abs_sum_by`, `avg_by`, `w_avg_by`,
   `median_by`, `var_by`, `std_by`, `percentile_by`, `count_by`, `join`, `natural_join`,
   `exact_join`, `sort`.

S3 registrations live in `NAMESPACE`: `head`, `tail`, `dim`, `as.data.frame`, `as_arrow_table`,
`as_record_batch_reader`, `as_tibble` are `S3method(...)`. `nrow` and `ncol` are **not** generic in
base R, so `nrow.TableHandle` / `ncol.TableHandle` are plain exported functions
(`export(nrow.TableHandle)`); `nrow(th)` still works because base R's `nrow()` goes through
`dim()`, and `dim.TableHandle` is registered.

`merge_tables(...)` is the free-function form of `th$merge(...)`; both flatten their arguments with
`unlist(c(...))` so you can pass handles, lists of handles, or a mix.

## 5. The Rcpp bridge

Everything C++ lives in the single file `rdeephaven/src/client.cpp`. Its shape:

1. Forward declarations of the wrapper classes and three
   `convertRcppListToVectorOfType{Aggregate,TableHandle,UpdateByOperation}` helpers. Each helper
   walks an `Rcpp::List`, pulls `.pointer` out of each element's `Rcpp::Environment` (that is where
   an Rcpp module object keeps its `XPtr`), and copies out the wrapped C++ object. This is the
   standard way a list of R6-wrapped objects becomes a `std::vector` for the C++ API.
2. `AggregateWrapper` + 13 `INTERNAL_agg_*` free functions returning `new AggregateWrapper(...)`.
3. `UpdateByOpWrapper` + `INTERNAL_opControlGenerator` + 34 `INTERNAL_*` update-by free functions.
   `INTERNAL_opControlGenerator` and `INTERNAL_delta` translate R strings
   (`"skip"`, `"throw"`, `"decimal128"`, `"null_dominates"`, …) into the C++ enums
   `BadDataBehavior`, `MathContext`, `DeltaControl`. **These string tables are duplicated in R**
   (`R/operation_control.R` validates the same sets), so a new enum value needs both sides.
4. `TableHandleWrapper` — one thin method per table operation, plus `IsStatic`, `NumRows`,
   `NumCols` (which is `Schema()->NumCols()`, i.e. a Flight `GetSchema` round trip on first call),
   `BindToVariable`, and `GetArrowArrayStreamPtr` (§6).
   `Sort` is the one method with real logic: it broadcasts a length-1 `descending` / `abs_sort` over
   all columns and builds `SortPair::Ascending` / `SortPair::Descending`.
5. `ClientOptionsWrapper` — one-line forwarders to `deephaven::client::ClientOptions`, except
   `SetBasicAuthentication`, which base64-encodes the token (`Base64Encode`) and sends it as a
   `"Basic"` custom authentication value.
6. `ClientWrapper` — two constructors (target+options, or adopt an existing `SEXP` external pointer),
   the table-creating methods, `RunScript`, `CheckForTable`, the two Arrow-stream methods, `Close`.
   It holds `Rcpp::XPtr<Client> internal_client` and a `const TableHandleManager
   internal_tbl_hdl_mngr = internal_client->GetManager();` member — the manager is captured once at
   construction.
7. The `RCPP_MODULE(DeephavenInternalModule)` block: `RCPP_EXPOSED_CLASS` declarations followed by
   `class_<T>(...)`/`.method(...)`/`function(...)` registrations. **This block is the ABI between R
   and C++** — if a name here does not match the name the R layer calls, you get a runtime error, not
   a compile error (see §12).

`R/exports.R` contains the single line `loadModule("DeephavenInternalModule", TRUE)`, which is what
makes `INTERNAL_Client` etc. visible to the package namespace. `src/RcppExports.cpp` is generated by
`Rcpp::compileAttributes()`; because this package uses a module rather than `// [[Rcpp::export]]`
attributes, that file only registers the module boot symbol and essentially never changes.

## 6. Data transfer: the Arrow C stream interface

Table data never crosses the boundary as R vectors. Both directions use the
[Arrow C stream interface](https://arrow.apache.org/docs/format/CStreamInterface.html): an
`ArrowArrayStream` C struct is heap-allocated in C++, handed to R as an `Rcpp::XPtr<ArrowArrayStream>`,
and the R `arrow` package imports/exports through it. No data is copied at the language boundary.

**Server → R** (`TableHandle$as_record_batch_reader()`):

```
TableHandleWrapper::GetArrowArrayStreamPtr()
  → internal_tbl_hdl.ToArrowTable(/*cooked=*/true)     // C++ client does the Flight DoGet
  → arrow::TableBatchReader → RecordBatchVector → RecordBatchReader
  → arrow::ExportRecordBatchReader(reader, stream_ptr)
  → Rcpp::XPtr<ArrowArrayStream>(stream_ptr, true)     // 'true' = R frees it
R side: arrow::RecordBatchStreamReader$import_from_c(ptr)
```

`as_arrow_table()`, `as_tibble()`, and `as_data_frame()` all build on that reader.

The `cooked = true` argument matters: it makes the C++ client materialize dictionary-encoded,
run-end-encoded, and doubly-encoded `RunEndEncoded<Dictionary<...>>` columns into plain value
columns before R sees them, so the R `arrow` package never has to deal with them.
`inst/tests/testthat/test_encoding.R` is the regression test for exactly that, and it builds the
encoded tables server-side via a `jpy` Python script. See `cpp-client/DESIGN.md` §8 for the
decoding machinery.

**R → server** (`Client$import_table()`):

```
ClientWrapper::NewArrowArrayStreamPtr()          // allocate an empty struct, hand R the XPtr
R side: rbr$export_to_c(ptr)                     // R fills it in
ClientWrapper::NewTableFromArrowArrayStreamPtr(ptr)
  → arrow::ImportRecordBatchReader(ptr)
  → manager.NewTicket() + ConvertTicketToFlightDescriptor
  → FlightClient()->DoPut(...), WriteRecordBatch per batch, DoneWriting, Close
  → manager.MakeTableHandleFromTicket(ticket)
```

Note this is a hand-rolled DoPut using `CreateFlightWrapper()` + `AddHeaders()`, not the C++ client's
`TableMaker`. The imported table is **not** bound to a server variable — call
`th$bind_to_variable(name)` if you want it visible to other clients.

## 7. Generator objects: AggOp, UpdateByOp, OperationControl

The `agg_*`, `uby_*`, and `op_control()` functions are *generators*: they return an opaque object
that is later handed to `agg_by()` / `agg_all_by()` / `update_by()`. Users never construct the R6
classes directly, and each class's `initialize` says so.

The three families are deliberately similar but **not** identical:

| | `AggOp` (`agg_ops_wrapper.R`) | `UpdateByOp` (`update_by_ops_wrapper.R`) | `OperationControl` (`operation_control.R`) |
|---|---|---|---|
| Constructed with | the `INTERNAL_agg_*` **function** plus its args, called lazily inside `initialize` via `do.call` | an **already-constructed** `Rcpp_INTERNAL_UpdateByOp` | an already-constructed `Rcpp_INTERNAL_OperationControl` |
| Extra state | `.internal_num_cols`, `.internal_agg_name` | none | none |
| Why | `agg_by()` must reject a zero-column aggregation, and needs the function's name for the error message | — | — |

That extra state is used in `TableHandle$agg_by()`, which loops over the aggregations and errors if
any has `.internal_num_cols == 0` — an empty `cols` is only meaningful in `agg_all_by()`, where the
aggregation applies to all non-grouping columns.

`update_by()` and `agg_by()` both normalize with `c(ops)` and then `lapply(ops, strip_r6_wrapping)`
to get a plain list of Rcpp objects for the module method.

Counts to sanity-check against `NAMESPACE`: 13 `agg_*` functions, 34 `uby_*` functions,
`op_control`, `merge_tables`, plus `Client`, `TableHandle`, `AggOp`, `UpdateByOp`,
`OperationControl`.

## 8. Argument validation

`R/utility_functions.R` provides a small validator vocabulary used at the top of essentially every
public method:

- `verify_type(arg_name, candidate, is_scalar, required_type, type_message, descriptor_message)` —
  the workhorse; handles both scalars and vectors/lists.
- Wrappers: `verify_string`, `verify_bool`, `verify_real`, `verify_any_int`, `verify_nonnegative_int`,
  `verify_positive_int`, `verify_in_unit_interval`, `verify_named_list`, `verify_int`,
  `verify_in_range`.
- Message builders: `vector_wrong_type`, `vector_wrong_element_type_or_value`,
  `vector_needed_scalar`, `scalar_wrong_type`, `scalar_wrong_value` — these exist so that error text
  is uniform across the whole package. Reuse them rather than writing bespoke `paste0` messages.
- `first_class(x)` = `class(x)[[1]]`; `strip_r6_wrapping(x)` = `x$.internal_rcpp_object`.

Convention: validate in R, before the call reaches C++, so users get an R-idiomatic error naming the
offending argument. `verify_type` is documented as not behaving correctly when `required_type` is
`"list"`, because of R's coercion rules.

## 9. Docs, man pages, and the pkgdown site

Documentation is roxygen2 comments in `R/*.R`. They are the source of truth for **both** `man/*.Rd`
**and** `NAMESPACE` — neither file should be hand-edited.

- Regenerate: `roxygen2::roxygenize()` (that is all `r-doc.sh` does). In CI the `rClientDoc` Gradle
  task runs it in Docker and copies the result back into `rdeephaven/man/`.
- `DESCRIPTION` pins `RoxygenNote: 7.2.3`; regenerating with a different roxygen version will churn
  every `.Rd` file.
- R6 classes are documented with `@docType class`, `@usage NULL`, `@format NULL` and per-method
  `#' @description` blocks; exported functions use the `@name` / `@title` / `@description` /
  `@details` / `@param` / `@return` / `@examples` / `@export` pattern. Runnable-looking examples are
  wrapped in `\dontrun{}` because they need a live server (some placeholders are literally
  `print("hello!")`).
- The docs site is pkgdown: `pkgdown/_pkgdown.yml` groups the reference index into Core API /
  AggBy Operations (`starts_with("agg_")`) / UpdateBy Operations (`starts_with("uby_")`) / Utility
  Functions / Other Data Types. A new exported function whose name does not start with `agg_` or
  `uby_` must be added to that file explicitly or pkgdown will fail on an undocumented topic.
- Vignettes (`vignettes/*.Rmd`) are built at install time; `VignetteBuilder: knitr`. Building them
  needs OS packages `libxml2-dev` and `pandoc`.

## 10. Tests

`testthat` edition 3. `inst/tests/testthat.R` is the entry point (`test_check("rdeephaven")`);
`inst/tests/testthat/helper.R` provides `get_dh_target()` from `DH_HOST` / `DH_PORT`.

| File | Covers |
|------|--------|
| `test_client_wrapper.R` | connection options, `import_table` for each input type, `run_script`, `open_table`, `close` |
| `test_table_handle_wrapper.R` | metadata, conversions, S3 methods, `merge` |
| `test_table_ops.R` | the table operations, compared against dplyr equivalents |
| `test_agg_by.R`, `test_agg_ops_wrappers.R` | aggregation results and generator-function validation |
| `test_update_by.R`, `test_update_by_ops_wrappers.R` | update-by results (uses `zoo`/`lubridate`) and generator validation |
| `test_encoding.R` | RunEndEncoded / Dictionary / RunEndEncoded-of-Dictionary columns survive the round trip (§6) |

Standard shape: a `setup()` function builds several `data.frame`s, opens a `Client`, and
`import_table`s them; assertions compare against the equivalent dplyr computation on the local
data frame. Tests that need server-side state (`test_encoding.R`) create it with `client$run_script()`
against a Python session.

## 11. What is not exposed

Useful to know before you go looking. The C++ client supports these but `src/client.cpp` does not
wrap them:

- **Ticking subscriptions.** There is no wrapper for `TableHandle::Subscribe`/`Unsubscribe`, and
  therefore no R access to `TickingCallback` / `TickingUpdate`. `client$time_table()` creates a
  ticking table on the *server*, but R only ever sees point-in-time snapshots — re-run
  `as.data.frame(th)` to see new data. Adding subscriptions would mean crossing a callback from a
  C++ subscription thread into R, which is not thread-safe with R's interpreter.
- **Table operations**: `LazyUpdate`, `Aj`, `Raj`, `LeftOuterJoin`, `WhereIn`, `SelectDistinct`,
  input-table `AddTable`/`RemoveTable`, `TableHandleManager::InputTable`.
- **Accessors**: `ToClientTable`, `Schema()` (only `NumCols()` is reached), `Stream`/`ToString`,
  `GetTicketAsString`.
- **Client options**: `SetClientCertChain`, `SetClientPrivateKey` (so mTLS is not reachable),
  and the on-close callbacks (`AddOnCloseCallback`).
- The C-ABI interop layer in `cpp-client` (`deephaven/client/interop/*.h`) is **not** used here; this
  package binds the C++ API directly through Rcpp.

## 12. Conventions, gotchas, known latent bugs

Naming:

| Kind | Convention |
|------|------------|
| R functions, R6 methods, arguments | `snake_case` |
| R6 classes | `CamelCase` (`Client`, `TableHandle`, `AggOp`, `UpdateByOp`, `OperationControl`) |
| Rcpp module classes and free functions | `INTERNAL_` prefix (`INTERNAL_TableHandle`, `INTERNAL_agg_sum`) |
| C++ wrapper classes / methods | `CamelCase`; members `internal_*` |
| Aggregation / update-by generators | `agg_*` / `uby_*` prefixes (pkgdown groups on these) |
| Public R6 field holding the Rcpp object | `.internal_rcpp_object` |

Style: the R code follows the [Tidyverse style guide](https://style.tidyverse.org) via the `styler`
package — run `styler::style_pkg()` before committing (see `rdeephaven/BUILDING.md`). Nothing in the
build enforces it: `R/build.gradle` runs only the tests, and the C++ side is the same story (see
`cpp-client/DESIGN.md` §12).
There is no automated formatter for `src/client.cpp`; it uses 4-space indentation, unlike the
2-space Google style used in `cpp-client`.

Gotchas:

- **Module method names are checked at run time, not compile time.** A typo in either the
  `.method("...")` string or the R call site produces an error only when that path executes.
- `NAMESPACE` and `man/` are generated. Editing them by hand will be silently reverted the next time
  roxygen runs.
- `DESCRIPTION` version numbers (`Imports:`) are real constraints — `arrow (>= 12.0.0)` in particular,
  because the C-stream import/export API is used.
- The R `arrow` package and the C++ client's Arrow **are different Arrow builds** living in the same
  process. Only the C data interface (plain structs) crosses between them; do not try to pass
  `arrow::Table` C++ objects.
- `th$ncol()` triggers a Flight `GetSchema` RPC in the C++ layer the first time (memoized there).
- Adding a file to the package requires updating `R/build.gradle`'s `copyIn`/`copyFile` lists for the
  Docker build.
- `as_data_frame()` calls `as.data.frame()` twice, with a `TODO` noting that
  `as.data.frame()` on an Arrow table returns a tibble.

Known latent bugs (present as of this writing; verify before relying on the surrounding code):

- `R/client_wrapper.R:191,200` call `options$add_int_options(...)` / `options$add_string_options(...)`
  (plural), but the module registers `add_int_option` / `add_string_option` (singular) at
  `src/client.cpp:874-875`. Passing a non-empty `int_options` or `string_options` to `Client$new`
  therefore fails.
- `R/table_handle_wrapper.R:565` compares `length(abs_sort) != length(by)`, but the parameter is
  named `order_by`; the branch only runs when `length(abs_sort) > 1`.
- `R/utility_functions.R:66` references an undefined `range_message` variable in the
  `is_scalar && length != 1` branch of `verify_in_range`.
- `src/client.cpp:644` declares the adopt-an-existing-connection constructor as
  `Rcpp::XPtr<ClientWrapper>(sexp)` while storing into an `Rcpp::XPtr<Client>`; this round-trips
  through `SEXP`, so the declared template argument has no effect on behavior.

## 13. Recipes

**Add a table operation** (assuming the C++ client already has it — otherwise do
`cpp-client/DESIGN.md` §13 first):

1. `src/client.cpp`: add a `TableHandleWrapper::Foo(...)` method returning
   `new TableHandleWrapper(internal_tbl_hdl.Foo(...))`.
2. In the `RCPP_MODULE` block, add `.method("foo", &TableHandleWrapper::Foo)` to
   `class_<TableHandleWrapper>("INTERNAL_TableHandle")`.
3. `R/table_handle_wrapper.R`: add the R6 method with a roxygen block, `verify_*` calls for each
   argument, and `return(TableHandle$new(self$.internal_rcpp_object$foo(...)))`.
4. If it should also be a free function or S3 method, add it at the bottom of the file with `#' @export`.
5. Rebuild (`r-build.sh`), regenerate docs (`roxygen2::roxygenize()`), add a test in
   `inst/tests/testthat/test_table_ops.R`.

**Add an aggregation**: C++ free function `INTERNAL_agg_foo` returning
`new AggregateWrapper(deephaven::client::Aggregate::Foo(...))` → `function("INTERNAL_agg_foo", ...)`
in the module → `agg_foo <- function(cols = character())` in `R/agg_ops_wrapper.R` returning
`AggOp$new(INTERNAL_agg_foo, "agg_foo", cols = cols)` → roxygen block with `@export` → tests in
`test_agg_by.R` and `test_agg_ops_wrappers.R`. pkgdown picks it up automatically via
`starts_with("agg_")`.

**Add an update-by operation**: same shape, but `UpdateByOp$new(INTERNAL_foo(...))` is called with an
already-constructed object (§7), and the function name must start with `uby_`.

**Add an enum-valued option**: add the string→enum mapping in `src/client.cpp` *and* the accepted-value
check in the corresponding R function (`op_control()` in `R/operation_control.R`, or the `uby_delta`
`delta_control` argument) — the two lists are independent and must be kept in sync.

**Debug a crash**: the problem is almost always in C++. `rdeephaven/BUILDING.md` has the Valgrind
(`R -d valgrind`) and gdb (`R -d gdb`, then `run`) recipes. For wire-level problems set
`GRPC_VERBOSITY=DEBUG`, which also turns on the C++ client's own logging.

**Diagnose `libdhclient.so: cannot open shared object file`**: `LD_LIBRARY_PATH` is not set in the R
session — `source $DHCPP/env.sh` before starting R, or use the `.Renviron` recipe.
